# GalleryApp — working agreement

OpenCode reads this file at the start of every session. It is the spec and the rules;
if a request conflicts with this file, ask before acting.

## Product

Three-screen iOS gallery app:

1. Gallery — grid of thumbnails from Unsplash, 30 per page, infinite scroll,
   favourite badge on thumbnails, tap opens Detail.
2. Detail — large image, title + description, heart toggle, horizontal swipe between
   images in the loaded set, photographer attribution linking to their Unsplash profile.
3. Favourites — grid/list of favourited images, remove from favourites, persisted locally.

Every screen works in portrait and landscape, on iPhone SE-class through Pro Max widths.
Layouts adapt with size classes; no hardcoded screen widths.

## Non-negotiables (from the assignment)

- Swift, iOS 17+, UIKit for screens (SwiftUI only for a small component if justified).
- Architecture MVVM.
- `URLSession` for networking; Core Data for persistance.
- Combine for reactive approach.
- `async/await` for asynchronous work.
- Unit tests with XCTest; at least one test per view model and for the persistence layer.
- SwiftLint with a committed `.swiftlint.yml`.
- No third-party packages.
- Follow OOP priciples and common design patterns, apply SOLID principles.
- Only the **public** Unsplash access key reaches the app (`Config.xcconfig` → `Info.plist`).
  The secret key never enters the app, the repo, or a commit. No user OAuth flow.
- Image URLs returned by the API are loaded directly and the `ixid` parameter is preserved
  when they are adjusted — Unsplash requires hotlinking.
- A missing or invalid key shows a configuration/error state; it is never a crash and never
  breaks `xcodebuild test`.
- `.gitignore` is committed and covers DerivedData, `.build`, `xcuserdata`,
  `Config.xcconfig` and `.DS_Store`.

## Architecture

- Layers: Presentation (ViewController + ViewModel), Domain (models, protocols, use cases),
  Data (Unsplash client, Core Data stack), Core (networking, image loading, DI).
- A ViewController renders and forwards events only. No networking, no persistence,
  no formatting logic in a view controller.
- Each screen has a ViewModel exposing `@Published` state and `AnyPublisher` outputs;
  the controller subscribes with `sink` and stores cancellables.
- Navigation through coordinators (`AppCoordinator`, `GalleryCoordinator`). View controllers
  never push or present other view controllers themselves.
- Every dependency is a protocol injected through the initializer; the composition root is
  `SceneDelegate`/`AppDelegate`, with the concrete types assembled there only.
- Networking returns domain models; decoding lives in the data layer. No `JSONDecoder`
  in a view model.
- Persistence is hidden behind `FavouritesRepositoryProtocol`.
- Image loading goes through `ImageLoading` (`NSCache` + `URLSession`), cancels in-flight
  requests on cell reuse, and never loads full-size images for thumbnails.

### Patterns to demonstrate

- Observer — Combine publishers carrying state from repositories and use cases to view models.
- Delegate — collection view data source/delegate, image-loading completion and cancellation.
- Factory — coordinator and dependency-container factories that build view controllers and
  view models.
- Dependency Inversion — every collaborator behind a protocol, injected at the composition root.
- Singleton only for a genuinely process-wide resource (for example the Core Data stack),
  and even then injected rather than reached through `.shared` from feature code.

### Error handling

- Every failure is a typed error (`APIError`, repository errors) mapped once, in the view
  model, to a user-visible state with a retry action.
- No `try!`, no force unwrap, no silent `catch {}`.
- Network, decoding and persistence failures never surface as raw errors in the UI.

## Commands

Regenerate the project from project.yml:

```bash
xcodegen generate
```

Build:

```bash
xcodebuild -project GalleryApp.xcodeproj -scheme GalleryApp \
  -destination 'platform=iOS Simulator,name=iPhone 17' -derivedDataPath .build build
```

Test:

```bash
xcodebuild -project GalleryApp.xcodeproj -scheme GalleryApp \
  -destination 'platform=iOS Simulator,name=iPhone 17' -derivedDataPath .build test
```

Lint:

```bash
swiftlint --strict
```

Screenshot for the README:

```bash
xcrun simctl io booted screenshot docs/screenshots/gallery.png
```

Do not launch Simulator.app. `xcrun simctl` is fine when a run is needed.

## Test plan

- XCTest only; no third-party test frameworks.
- Minimum: one test file per view model and a full suite for the persistence layer.
- Also cover: Unsplash decoding and error mapping, image cache hit/miss/cancellation,
  pagination edge cases.
- Tests never touch the network or the real API: `URLProtocol` stubs and JSON fixtures for
  networking, an in-memory Core Data store for persistence.
- Live API checks are manual only — demo keys are limited to 50 requests per hour.

## Submission and README

The deliverable is a GitHub repository URL, so the repository is part of the mark.
`README.md` at the root contains:

1. Contact — author name and a profile link.
2. Overview — what the app does, in one paragraph.
3. Assumptions and extra features beyond the brief, listed explicitly.
4. Key functionality — paginated gallery, detail swipe, persisted favourites, badge sync.
5. Solutions overview — MVVM + coordinators + DI, UIKit/Combine/Core Data/URLSession,
   design patterns used and where, and how the architecture improves code quality,
   maintainability and scalability; explicitly "no third-party packages".
6. Screenshots or a demo video of all three screens.
7. Configuration — create `Config.xcconfig` from the example, add the public access key,
   run `xcodegen generate`, build and run.
8. Build, test and lint commands, the test inventory, and the commit convention
   (`[ADDED]` / `[FIXED]` / `[REFACTORED]` / `[TESTED]` / `[DOCS]` / `[CHORE]`).

The README is updated in the same branch as the behaviour or configuration it describes,
never "later". A stale README is a failed milestone.

## Definition of done for any task

- Project builds for the simulator with no new warnings.
- `xcodebuild test` passes.
- `swiftlint --strict` reports zero violations.
- README reflects current behaviour, configuration and screenshots.
- The app runs on the iPhone 17 simulator in both portrait and landscape.
- No access key, secret, token or key-bearing URL exists in tracked files.
- The test suite performs no live network calls.

## Git flow and pull requests

The assignment requires a visible Git flow with feature branches and pull requests, even
though no formal code review takes place.

- `main` is the only long-lived branch and always holds a buildable, testable app.
- Every slice starts from `main` on `feat/<slice>`, `fix/<slice>`, `chore/<slice>`,
  `test/<slice>` or `docs/<slice>`, and ends in exactly one pull request back into `main`.
- One PR = one slice = a reviewable diff. Never bundle unrelated work.
- The PR title uses the commit format, for example `[ADDED] paginated gallery grid`.
  The PR body states what changed, why, and the verification performed (build, tests,
  lint), plus screenshots for UI changes.
- Self-review the diff before handing the branch over.
- The agent prepares the branch, the commit history and the PR description, then stops.
  The human pushes and opens the PR.
- Never commit, merge or push to `main` directly. Never force-push, rebase or amend
  published history.
- Every merge into `main` satisfies the definition of done. Nothing half-finished is merged.
- Tag the final submission `v1.0.0`.

### Commit messages

- Format: `[TAG] past-tense verb + summary`, subject under 72 characters.
- Tags: `[ADDED]` new feature, `[FIXED]` bug fix, `[REFACTORED]` restructure with no
  behaviour change, `[UPDATED]` changed behaviour or dependency, `[TESTED]` tests only,
  `[DOCS]` documentation only, `[CHORE]` tooling, project or configuration.
- Examples: `[ADDED] paginated gallery grid`, `[FIXED] kept heart state after detail swipe`.
- The brief also references Conventional Commits; the bracket prefixes it prints are the
  canonical style here. Mapping if ever needed: `feat` → `[ADDED]`, `fix` → `[FIXED]`,
  `refactor` → `[REFACTORED]`, `test` → `[TESTED]`, `docs` → `[DOCS]`.
- One logical change per commit; explain *why* in the body when it is not obvious.
- No mega-commits, no WIP commits, no "fix typo" noise in the final history.

## Rules

- Never edit `GalleryApp.xcodeproj` by hand. Change `project.yml` and run `xcodegen generate`.
- The Unsplash access key lives in `Config.xcconfig` (gitignored) and reaches code through
  `Info.plist`. `Config.xcconfig.example` is committed with an empty value.
- Never hardcode a key, token, or URL with a key in it.
- Never call the live Unsplash API from tests, CI or retry loops; cache pages and images.
- Do not reformat or refactor files unrelated to the current task.
- Ask before: changing architecture, adding a target, adding a dependency, changing this file.
- Keep photo metadata (id, title, description, URLs) in Core Data — never store image files.
- Keep every screen adaptive: size classes, Dynamic Type, VoiceOver labels.
